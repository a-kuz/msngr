# Три реакции в диалоге на двоих: диагноз

Симптом со скриншота владельца: под сообщением в диалоге на двух участников
одновременно `👍2` и `❤️` — сумма счётчиков 3 при двух участниках.

Проверялись две гипотезы: наследование чужой базы при повторной регистрации (A)
и ошибка учёта при смене реакции (B).

**Верна A.** Гипотеза B не подтвердилась ни в одном из прогнанных сценариев.

Скриншоты — в `2026-08-15-reactions-diagnosis/`.

## Стенд

Свои симуляторы `msngr-rx-A` (9732467E) и `msngr-rx-B` (BAD3A81A), iPhone 17,
iOS 26.5, удалены после прогона. Свой `wrangler dev` на :8809 с отдельным
`--persist-to` (схема D1 накатывалась `wrangler d1 execute msngr --local
--persist-to ... --file schema.sql`, без неё регистрация отвечает 500).
Приложение запускалось через `SIMCTL_CHILD_MSNGR_SERVER=http://localhost:8809`,
сборка — HEAD `ca9eacd` в свой `derivedDataPath`. Юзеры: `rxalpha`
(01M01ZJN8AHPB3G803ES90BGG8), `rxbeta` (01M01ZKE9PX7M5E1XA450PA4GE), позже
`rxgamma` (01M02089DHDA71ET11V2W8DFR9). Чат создавался
`POST /api/chats` с токеном A. Состояние снималось прямо из
`msngr.sqlite` контейнера группы (копия, чтобы не мешать WAL).

## B: учёт при смене реакции — не воспроизводится

Чистая база, диалог `hello`, снимки после каждого шага (сумма — число userId во
всех массивах `message.reactions`):

| Шаг | Ожидание | Факт на A | Факт на B |
|-----|----------|-----------|-----------|
| B ставит 👍 | 👍1 | 👍1 | 👍1 |
| A ставит 👍 | 👍2 | 👍2 | 👍2 |
| A меняет на ❤️ | 👍1 ❤️1 | 👍1 ❤️1 | 👍1 ❤️1 |
| A быстро 👍 → 🔥 подряд | 👍1 🔥1 | 👍1 🔥1 | 👍1 🔥1 |
| B снимает свою повторным тапом по капсуле | 🔥1 | 🔥1 | 🔥1 |
| B тапает чужую капсулу 🔥 | 🔥2 | 🔥2 | 🔥2 |
| A и B меняют одновременно (😂 и 😮) | 😂1 😮1 | 😂1 😮1 | 😂1 😮1 |
| перезапуск обоих приложений | без изменений | 😂1 😮1 | 😂1 😮1 |
| сброс `syncedSeq` на B → сервер переигрывает всю историю по WS | без изменений | 😂1 😮1 | 😂1 😮1 |

Инвариант «не больше одной реакции на пользователя» держится потому, что
единственный писатель поля — `SyncEngine.applyReaction`
(`ios/MsngrKit/Sources/MsngrCore/SyncEngine.swift:1119`): он сначала вычищает
userId из всех эмодзи, потом добавляет в новую. Через него идут все пути —
локальная отправка (`enqueue`, SyncEngine.swift:722), живой фрейм
(`applyContent`, :529), историческое применение (`storeHistoric`, :585) и
отложенное (`applyBuffered`, :1174). Юнит-тесты этих веток (`HistoricReplayTests`,
`ServiceFrameTests`) проходят: `swift test --filter
"HistoricReplayTests|ServiceFrameTests"` — 6 из 6.

Пагинацию вверх (`storeHistoric`) вживую проверить не удалось по другой причине:
после удаления сообщения из локальной БД клиент запросил `/history`, получил 10
конвертов и не сохранил ни одного — ключи ратчета для уже расшифрованных
сообщений израсходованы. Это отдельное наблюдение, к счётчикам отношения не
имеет, но означает, что ветка `storeHistoric` на практике работает только для
сообщений, которые клиент ещё не расшифровывал.

## A: наследование чужой базы — воспроизводится один в один

1. На A с живой сессией `rxalpha` удалён `session.json` из контейнера группы
   (имитация прежнего поведения, когда сессия не сохранялась), приложение
   перезапущено → экран регистрации, `msngr.sqlite` на месте
2. Регистрация нового пользователя `rxgamma`. Сразу после неё открывается список
   чатов со старым диалогом, вся переписка и реакции прежней личности на месте
   alpha и beta, gamma нет нигде.
3. Gamma ставит 😂 на унаследованное сообщение →
   `{"😮":["…beta"],"😂":["…alpha","…gamma"]}`, сумма 3. На экране `😂 2` и `😮`
   под одним сообщением в диалоге, который выглядит как разговор на двоих

Реакция gamma при этом не ушла на сервер: gamma не участник чата, запись в
`outbox` осталась в состоянии `inflight`, у пира счётчик не изменился. То есть
лишний счётчик существует только на этом устройстве.

### Где в коде

- `ios/Msngr/Onboarding/RegisterView.swift:82` — регистрация открывает
  **существующую** БД контейнера (`AppState.storage` → `AppDatabase.open`) и
  берёт из неё identity; ничего не стирается.
- `ios/Msngr/App/AppState.swift:62` `saveSession` — записывает новую сессию и
  поднимает ядро поверх старых данных. Стирание есть только в
  `resetToRegistration()` (`AppState.swift:87`, вызывается из `logout()` и
  `finishRevokedSession()`), то есть покрыт только осознанный выход и отзыв
  устройства.
- `ios/Msngr/App/AppState.swift:44` `loadSession` — если файла нет или он не
  читается, приложение молча уходит на регистрацию, база остаётся.
- Хранилище ничем не привязано к аккаунту: маркера владельца (например в `kv`)
  нет, `AppDatabase.open` его не проверяет.
- Итог для счётчика: `SyncEngine.applyReaction` различает людей строго по
  userId, а в массивах остаются userId прежних личностей, которых в `member`
  уже нет. Счётчик капсулы — длина массива (`BubbleLayout.swift:185`), поэтому
  сумма легально превышает число участников.

## Предлагаемый фикс (не применён)

Привязать локальное хранилище к аккаунту и стирать его при смене владельца:

1. При bootstrap писать в `kv` маркер `ownUserId`.
2. В `RegisterView.register()` — **до** `AppDatabase.open` и генерации ключей —
   сравнивать маркер: если файл БД есть и маркер не пустой, вызывать
   `AppContainer.wipe(AppState.storage)`. Новый аккаунт никогда не наследует
   данные легально, поэтому условие можно свести к «идёт регистрация, а данные
   в контейнере уже есть».
3. Тем же путём обрабатывать нечитаемый `session.json` в `loadSession`: не
   молчаливый уход на регистрацию поверх чужих данных, а тот же wipe.

Порядок важен: identity создаётся в той же БД внутри `register()`, стирание
после `store.identity()` уничтожит только что сгенерированные ключи.

Проверять фикс тем же прогоном: удалить `session.json`, перезапустить,
зарегистрировать нового юзера — список чатов должен быть пуст.
