# Badge on the app icon: live run

Date: 2026-08-15. Stand: own `wrangler dev` on :8809 with its own `--persist-to`,
own `apns-mock` on :9873, own simulator `badge-agent` (iPhone 17, iOS 26.x),
deleted after the run.

## What was checked

The icon carries the unread count the server computed and sent in the push, and
it does not walk backwards while messages arrive.

The sender is a second account driven from a node script over the socket. Its
envelopes are placeholders, so the receiving app stores no message rows at all
(`SELECT count(*) FROM message` = 0 after the run) — the run says nothing about
previews, only about the count.

| step | what was done | icon |
|---|---|---|
| 1 | chat request accepted and read in the app | no badge |
| 2 | app killed, 5 messages sent | 5 |
| 3 | still killed, 6 more sent | 11 |
| 4 | app launched, chat opened | 1 |

Steps 2 and 3 are the case the fix is about: the app was not running, nothing on
the device could count anything, and the number on the icon was still right
both times. Step 4 is the app lowering the count from its own reading.

The 1 left at step 4 is the app's own `chat.unreadCount`, which stayed at 1 with
`lastSeq = myReadUpTo = 57`. Its cause was not established; the placeholder
envelopes never became messages, so the chat's bookkeeping ran on input it never
gets in normal use.

## What the simulator cannot show

`xcrun simctl push` does not start the notification service extension
(`docs/research/nse-simulator-experiment.md`), so the ordering guard the
extension applies was not exercised. The evidence is direct: after 19 pushes the
`badge` row in the shared database read `value=1 stamp=0`, and only the app
writes with stamp 0. Everything that landed on the icon from a push landed there
because SpringBoard applied `aps.badge` itself, with nothing in between.

So on the simulator a burst can still put an older count on the icon: the mock
delays each push by a random 150–500 ms and thereby reorders bursts sent closer
together than that. On a device the extension runs, `BadgeStore.applyFromPush`
drops the overtaken count, and the icon follows the order the server produced.
That path waits for hardware.

The server side is covered without a device: `server/test/smoke.mjs` checks the
badge in the payload (0 before the chat is accepted, 1 after a read) and that
`badgeStamp` grows across pushes. `BadgeStoreTests` covers the ordering itself,
including a shuffled burst of 60 counts and an offline burst that collapses to
one push.

## APNs mock under load

`server/test/apns-mock-load.mjs` drives the mock at ~100 pushes/s against a
shimmed `xcrun`, well above what its pool can deliver:

```
accepted=400 delivered=100 failed=0 dropped=300 (rate=0 overflow=300)
queued=0 active=0 peak(queued=32 active=4)
```

Live child processes sampled during the burst peaked at 4, the configured
concurrency. Before the change the mock spawned one `xcrun simctl push` per
notification: a run at ~11 msg/s piled up 1100–1200 of them, exhausted the
host's IOSurface client pool, and every CoreSimulator client on the machine
failed to start for about half an hour.
