# Passcode: setup, repeat, check, auto-lock — run

The simulator `fable-solo` (iPhone 17 / iOS 26.5) as the fixture account
`alfa`. Some screenshots carry the session's tap grid; the two strips are
consecutive frames of a 15 fps screen recording. The passcode was removed at
the end of the run, so the fixture home comes back unlocked.

## Setting the passcode

- Settings → «Безопасность» → the «Код-пароль» toggle opens the pad with
  «Придумайте код-пароль».
- `01-setup-repeat-stage.png` — four digits in, the pad asks «Повторите
  код-пароль» with the dots cleared.
- `02-setup-mismatch-reset.png` — a repeat that does not match: the pad drops
  back to «Придумайте код-пароль» with empty dots, and nothing is saved.
- A matching repeat lands back in settings with the toggle on and the
  «Face ID» row unfolded below it.

## The lock

- `03-cold-start-locked.png` — the app killed and launched again: the lock
  screen over the blurred list, «Введите код-пароль».
- `04-wrong-pin-cleared.png` — a wrong code filling the dots and being
  rejected: the dots clear, the lock stays.
- `05-unlock.png` — the right code: the dots fill and the last frame is the
  chat list.
- `06-autolock-after-background.png` — home button, 36 s in the background,
  the app brought back: locked again (the 30 s auto-lock grace period).
- Turning the toggle off removes the passcode; the next cold start opens
  straight into the list.

## Face ID

Driven later the same evening through Simulator.app's Features → Face ID menu
(Enrolled, then a face per scenario), with the Face ID toggle on under the
passcode:

- `07-faceid-prompt.png` — a cold start invokes the scan on its own: the lock
  screen with the system Face ID HUD over the pad.
- `08-faceid-unlocked.png` — Matching Face: the chat list, no code typed.
- `09-faceid-rejected.png` — Non-matching Face: «Лицо не распознано» with
  «Повторить Face ID» and «Отменить», the lock stays; cancelling falls back to
  the pad and the code unlocks as usual.

The passcode and the Face ID toggle were turned off again at the end, so the
fixture home comes back unlocked.

An observation for the process, not the product: during this run roughly two
`idb` taps out of three never reached their control — the app log shows the
touch arriving and the final event swallowed as a system gesture
(`systemGestureStateChange: 1; shouldSend: 0`). The host's load average stood
around 40 at the time, but a controlled comparison on the XCUITest side found
its own lost taps unchanged at load 6 (their cause was a microphone permission
lost after an uninstall), so load remains a suspicion here, not a mechanism.
Retry-until-the-value-changes is what this run did about it.
