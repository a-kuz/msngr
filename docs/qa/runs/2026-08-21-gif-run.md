# An animated GIF keeps its animation, 2026-08-21

The owner reported a GIF arriving as one static frame. The cause was on the
sending side: every picked image went through `ImageProcessor.prepareForSending`,
which re-encodes as JPEG — a format with one frame. Nothing downstream could
have animated what was already flattened.

What changed (`27daed3`): a file whose bytes start with `GIF8` and whose source
holds more than one frame is stashed and sent as it came, with `image/gif` as
its mime; the JPEG pass is skipped. In the feed the tile that would have shown
a still is driven by `GIFAnimation`, a frame loop over `CGImageSource` that
reads each frame's own delay and holds one decoded frame at a time. It stops
with the cell (`teardownAutoplay`) and stands still off-screen through the
`setAutoplayActive` the video autoplay already uses. At full screen the same
loop plays inside a `UIImageView` instead of `AsyncImage`, which would have
shown the first frame and nothing else.

## The run

A simulator of its own (`disp-gif`, iPhone 17), the bravo fixture home, and a
two-second 8 fps GIF (45 KB, `GIF89a`, a moving test pattern) put into the photo
library with `simctl addmedia`. Sent into the Random group through the attach
menu; it left with a tick.

- The feed animates: three screenshots 0.6 s apart, cropped to the same strip
  inside the bubble, hash differently, and the gradient band has visibly moved
  between them (`2026-08-21-gif/01-feed-frame-a.png`,
  `02-feed-frame-b.png`).
- The viewer animates: a tap opens the GIF full screen and four frames sampled
  0.5 s apart are four different pictures (`03-viewer.png` is one of them).
- The bubble keeps the tick and the time: the message travelled as a photo
  message, only its bytes and mime changed.

Not covered by this run: an incoming GIF from another device (the sending side
is what was broken, and the receiving path reads the same mime), and a GIF sent
as part of an album.
