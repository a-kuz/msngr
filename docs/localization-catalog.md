# Moving interface text into a string catalog

Raised while translating the repository to English, 2026-08-16. Nothing here is
implemented; this is the brief for the task.

## Where the strings are now

Every user-visible string is a literal at its call site. Measured on this branch:
411 string literals containing Cyrillic across the Swift sources, 288 of them
distinct. They sit in three bundles:

- the iOS app, `ios/Msngr/` — the bulk of it, with `Screens/ChatInfoView.swift`
  (45 literals), `Screens/SettingsView.swift` (29), `Chat/ChatScreen.swift` (27)
  and `ChatList/ChatListView.swift` (25) at the top;
- the core library, `ios/MsngrKit/Sources/MsngrCore/` — `NotificationContent.swift`
  (the banner text the NSE and the app both build), `SendFailure.swift`,
  `ChatSettings.swift`, `ChatPrivacy.swift`. These reach the screen through two
  processes, so the catalog has to be readable from the extension as well;
- the macOS client, `ios/MsngrMac/MacViews.swift` (30 literals).

Plus the Info.plist usage descriptions. Those are generated by xcodegen from the
`info.properties` blocks in `ios/project.yml` (lines 44–48 for the app, 108 for
macOS), so `ios/Msngr/Info.plist` and `ios/MsngrMac/Info.plist` are outputs and
editing them does nothing.

`CFBundleDevelopmentRegion` is `$(DEVELOPMENT_LANGUAGE)`, and our sources contain
no `.lproj`, `.strings`, `.stringsdict` or `.xcstrings` file at all. The base
language is de facto Russian.

## What stops a mechanical replacement

**Tests match on text.** `ios/MsngrUITests/SmokeTests.swift` finds elements by
accessibility identifier almost everywhere (`chat.input`, `chatlist.new`,
`reg.submit`), but six lookups go by the visible string: `"Чаты"` (lines 38, 89),
`"Юзернейм или имя"` (51), `"Ответить"` (108, 112) and `"Фото или видео"` (119,
120). Each of those needs an identifier on the element before the string moves.

**Unit tests assert Russian output.** 51 lines compare against the shipped text:
`NotificationContentTests` (14), `BubbleLayoutTests` (11),
`MessageSelectionTests` (10), `UnreadMarkerStateTests` (6), `LastSeenTests` (5),
`SendFailureTests` (4), `ChatFeedTests` (1). These check real behaviour, not
fixtures, so they move together with the strings they check.

**Plurals are hand-written.** `MessageSelection.title(count:)`
(`Chat/MessageSelection.swift:32`) and `UnreadMarkerCell.title(count:)`
(`Chat/MessagesViewController.swift:669`) pick a form by `count % 100` and
`count % 10` — the Russian three-form rule, coded by hand. A catalog gives this
away through plural variations, and the hand rule has to go rather than be
translated.

**Gendered text.** `LastSeenTests` pins `"был(а) только что"`; the parenthesised
ending is the Russian workaround for not knowing the person's gender. English has
no such problem, but any third language will, and the catalog is where that is
solved.

**Counts inside interpolation.** `"\(members.count) участников"`
(`ChatViewModel.swift:409`, `ChatInfoView.swift:82`) is a plural rule hiding in a
format string; it needs the same treatment.

## Proposed shape

String Catalogs (`.xcstrings`), base language English, one per bundle:

- `ios/Msngr/Localizable.xcstrings` for the app and the extension (the NSE has no
  strings of its own — its text comes from MsngrCore);
- `ios/MsngrKit/Sources/MsngrCore/Resources/Localizable.xcstrings` for the core
  library. This needs a `resources:` entry on the `MsngrCore` target in
  `ios/MsngrKit/Package.swift` and lookups through `Bundle.module`, otherwise the
  extension process will not find the table;
- `ios/MsngrMac/Localizable.xcstrings` for the macOS client, unless the two
  clients are made to share one.

The Info.plist descriptions go into `InfoPlist.xcstrings` per target, and the
English source text is what stays in `ios/project.yml`.

Keys: the English text itself, which is what Xcode's catalog defaults to and what
keeps the call sites readable (`Text("Chats")`). A separate identifier scheme
buys nothing while there is one translation to maintain.

## Order of work

1. Put accessibility identifiers on the six elements `SmokeTests` finds by text,
   and switch the test to them. This is independent of everything else and can
   land first.
2. Add the catalogs and the `Bundle.module` plumbing, empty. Build.
3. Move strings a screen at a time, English as the base. Each step: replace the
   literals, update the unit tests that assert the old output, run
   `make check DEV_UDID=<simulator>`.
4. Replace the two hand-written plural helpers with catalog plural variations and
   delete the `% 100` / `% 10` arithmetic.
5. Move the Info.plist descriptions.
6. Add Russian as the second language, translating from the catalog rather than
   from the code.

Steps 1 and 2 are safe on their own. Step 3 is where the UI tests break if the
identifiers from step 1 were missed, which is why it comes after.

A unit test never asserts a user-visible string as a literal: the simulators on
this host inherit the Mac's Russian language, so `String(localized:)` resolves
the ru translation there and the en literal fails. The test compares against
`String(localized:)` with the same key — it then asserts which string the code
chose, in whatever language the host runs (`ChatSearchSessionTests` is the
pattern).

## Done means

`rg '[А-Яа-яЁё]' -g '*.swift' ios/` returns only `"рф"` in
`MsngrCore/Markdown.swift` (a top-level domain in the autolink table, not text),
the app runs in English on a device with an English locale and in Russian on a
Russian one, `make check` is green, and `ROADMAP.md` has the
"language choice and localization" line closed.
