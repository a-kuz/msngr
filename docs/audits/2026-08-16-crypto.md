# Crypto audit, 2026-08-16

Scope: `MsngrCrypto` (X3DH, Double Ratchet, sender keys, provisioning, media),
the `MsngrCore` side of it (`E2EEManager`, `IncomingDecryptor`, `IdentityStore`,
`CryptoGate`), and the server endpoints that carry keys (`/api/register`,
`/api/devices`, `/api/users/:id/prekeys`, `/api/provision/*`).

The adversary throughout is the server: it routes every envelope, serves every
public key, and an end-to-end messenger is what stands between it and the
plaintext.

## 1. The X25519 identity key is bound to nothing

A device identity is two independent pairs (`MsngrCrypto/Keys.swift`): X25519
for key agreement and Ed25519 for signatures. Nothing signed the X25519 half:
not registration, not `/api/provision/:id/claim`, not any DTO. The server stored
`identity_key` and `identity_sign_key` as two unrelated columns.

What trusted what:

- TOFU pinned the Ed25519 key only (`IdentityStore.checkTrust`, table
  `trustedIdentity`).
- The safety number was computed over the Ed25519 key only
  (`SafetyNumbers.generate`, called from `ChatInfoView`).
- The session secret came from the X25519 key (`X3DH.respond`, called from
  `IncomingDecryptor`).

So the value that decided who the peer is and the value that decided who could
read were different values. The Ed25519 key is public and the server hands it
out itself. An envelope carrying the victim's real `isk` and an attacker's `ik`
opened a session on attacker-held keys, `checkTrust` answered `.trusted`, no
warning was raised, and reading the safety number aloud could not have shown
it: full impersonation of any user towards any recipient.

The reverse direction was not readable by the attacker. As initiator we take
`dh1` and `dh3` against the peer's signed prekey, whose signature we verify
against the Ed25519 key, so a swapped `identityKey` in a bundle only breaks
delivery.

Fixed by signing the X25519 key with the Ed25519 key at registration and at
claim, verifying that signature wherever a peer's identity key is used, and
putting the X25519 key into the safety number.

## 2. The identity check was skipped when `isk` was absent

`IncomingDecryptor` ran its trust check inside `if let iskB64 = box.isk` with no
`else`. A prekey box that simply omitted the field built a session without
consulting `trustedIdentity` at all, pinned peer or not. Our own sender always
fills the field in, so the path was only reachable for a hand-built envelope —
the same adversary as above, one field cheaper.

Fixed by refusing a prekey box that does not carry an identity, its signature
and a passing trust check.

## 3. A replayed prekey envelope reset a live session

`DoubleRatchetSession.hasReceived` existed and no production code read it; the
only mention was a comment in `CryptoTests` referring to a `stale_pk_ignored`
branch of `E2EEManager` that was never written.

An old prekey envelope delivered a second time therefore reached the `pk` branch
(no live or archived session opens it) and `archiveCurrentSession` ran
unconditionally, before any candidate had decrypted anything:

- with the one-time prekey already spent the replay failed to open, but the copy
  was already in the archive, and repeats pushed the five archive slots full of
  duplicates of the live session, evicting the sessions that late messages are
  recovered through;
- with the prekey still in place a fresh responder session was saved over the
  live one. A responder session has no sending chain, so the next message to
  that peer failed with `noSession`.

Fixed by refusing the `pk` branch for a session that has already received, and
archiving only after a candidate has opened the message.

## 4. Device linking seals the account to a key the server chose

`Provisioning.seal` encrypts the account bundle — the identity private keys —
to a public key the approving device reads out of `/api/provision/lookup`. The
pairing code is server-generated and commits to nothing. A server that answers
the lookup with a key of its own receives `identityDH` and `identitySigning`:
not a man in the middle of one conversation, the account itself.

Not fixed in this branch. The fix is to carry the ephemeral public key in the QR
code, so it never passes through the server; tracked separately.

## 5. Smaller things

- `SenderKeyState.init` discarded the result of `SecRandomCopyBytes`. A failure
  would have left a chain key of 32 zero bytes with nothing said about it.
  Fixed: the status is checked.
- The sender key signature covered the ciphertext alone, leaving `keyId` and
  `iteration` unauthenticated, and the box carried no associated data. No attack
  follows — a receiver finds the chain by `(chatId, senderUserId, keyId)` and a
  changed iteration simply fails to open — but the signature now covers all of
  it. Fixed.
- `ratchetSession.theirIdentityDH` was written and never read; the incoming path
  filled it with `box.ik ?? ""`. Fixed: the column is gone.
- Skipped-key eviction in `DoubleRatchet` sorts by the message number parsed out
  of the map key and ignores the `dhPub` part of it, so with more than one chain
  present the keys dropped are not the oldest. Behaviour only; separate commit.
- The Double Ratchet associated data does not name the chat, so the server can
  present a direct message inside another chat. Nothing is disclosed by it;
  separate commit.
