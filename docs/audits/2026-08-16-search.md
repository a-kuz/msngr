# Search on the chat list — specification

Raised by the owner, 2026-08-16.

## What it has to do

Search everything from one field, the way people expect it to work.

**Case 1.** Someone types a name looking for a conversation. Chats matching by
name appear immediately. Meanwhile messages containing that word are searched in
the background and appear below the chats.

**Case 2.** Someone types a phrase that matches no chat name. They get the
full-text result over messages, and that is the whole answer — no empty screen
in between.

So: chats first and instantly, messages after and asynchronously, both in the
same list under section headers. The instant half must never wait for the slow
half.

## Where it stands

`ChatListModel.updateSearch()` filters the already-loaded chats by title and by
the peer's username. Nothing else is searched.

The full-text index already exists and is already maintained: `messageFts`, an
FTS4 virtual table synchronised with `message` (Database.swift, migration v1).
**Nothing in the app queries it** — this is the first use.

## Sections

- **Chats** — by title and by the peer's username. Instant, from what is loaded.
- **Messages** — full text over `messageFts`, with a snippet around the match and
  the match highlighted. Tapping opens the chat *at that message*, not at the
  bottom: the feed can already jump to a message and load history around it (see
  the reply-quote jump in ChatViewModel/MessagesViewController).
- **People** — users found by username on the server, as the new-chat sheet
  already does. Reuse that path rather than writing a second one.
- **Media, files, links** — the per-chat gallery is being built right now under
  a separate task; if its queries generalise across chats, use them, otherwise
  leave these sections out and say so.

## Things that decide whether it is good

- **Message requests.** A chat waiting to be accepted hides its content
  everywhere else (ChatPrivacy, `contentHidden`). Search must not be the hole
  that leaks it.
- **Debounce and cancellation.** Every keystroke must not start a new full-text
  query; an in-flight query for an older prefix must be dropped rather than
  arrive late and overwrite fresher results.
- **Size.** A chat of tens of thousands of messages is normal here. Page the
  message results and do not build them all before showing the first screen.
- **Ranking.** Recent matches first is the useful default; say what you chose.
- **Empty and partial states** in the product's voice: state, not apology. And
  "still searching messages" is a state worth showing while chats are already on
  screen.

## Out of scope for now

Search inside one chat is a separate item (`docs/audits/2026-08-16-chat-ui.md`,
item 4) — but if the two share a query layer, build it once and say so.
