# Media appears in the feed at the moment of sending

Owner's request, 2026-08-19 (`task.md`): a photo, an album, a video, or a pasted
image must show up in the feed the instant it is picked, blurred and correctly
framed, and fill in with the real preview as it becomes ready. Today the feed
stays empty for the whole preparation time — `ChatScreen.sendPhotos` only
enqueues the message once every attachment is compressed and, for video, fully
transcoded.

## Current shape

`ChatScreen.sendPhotos` / `sendVideo` / `sendImages` run the whole pipeline —
`loadTransferable` → `ImageProcessor.prepareForSending` → BlurHash → (video)
`AVAssetExportSession` — and only then call `model.enqueue(c)`, which writes
the `message` row (visible in the feed) and the `outbox` row (picked up by the
send worker) in one transaction. An album's items are processed sequentially,
so the first bubble cannot appear before the last item finishes.

`SyncEngine.enqueue` cannot be called earlier as-is: the `outbox` row it
creates is immediately eligible for the send worker, and `sendOutboxItem` /
`uploadPendingMedia` only upload a `MediaInfo` when `localPath` is set — if it
runs before the file is stashed, the worker sends the envelope with an empty
`mediaId`/`key`/`hash` instead of waiting. Splitting "row is visible" from "row
is sendable" is a real protocol requirement, not an incidental simplification.

## Design: one row, three phases

Replace the single `SyncEngine.enqueue` (for media) with three calls against
the same `clientMsgId`, so the feed row is created once and only ever updated
in place — never re-created:

1. **`beginMedia(clientMsgId:chatId:kind:text:media:album:)`** — writes the
   `message` row immediately (right kind, caption, N blank slots for an
   album), no `outbox` row. Layout already defaults to a 4:3 / square aspect
   when `w`/`h` are nil, so the bubble has a sane frame from the first frame.
2. **`updateMediaPreview(clientMsgId:media:album:)`** — updates `media`/`album`
   on the same row. Called once per attachment with a fast BlurHash + an
   approximate aspect, called again later with the true dimensions.
3. **`finalizeMedia(chatId:clientMsgId:content:)`** — once the attachment is
   compressed and stashed (`localPath` set), updates `media`/`album` one more
   time and only now writes the `outbox` row and wakes the worker.

`abandonMedia(clientMsgId:)` — if preparation fails (disk write, video export),
deletes the not-yet-queued row and surfaces the same alert `stash()` shows
today. Today a failure here means no row was ever created; now the row is
created optimistically and withdrawn on failure — same end state, the row
merely flashes briefly instead of never appearing.

`MessageCell.configureMedia` already keeps its image views in place across an
in-place reconfigure of the same message id (existing comment: "the same
message reconfigured in place ... keeps its media views"), so updates 1→2→3
render as a blur firming up into a photo, not a flash or a re-insert.

### Rejected alternative: UI-only optimistic bubble

Keep `SyncEngine` untouched; render a placeholder bubble purely in
`ChatViewModel` (never persisted) and swap it for the real message once
today's `enqueue()` completes. Smaller diff, but the swap crosses an
unavoidable async gap — `enqueue()`'s DB write and the feed's
`ValueObservation` both need a round trip before the real row appears — so
removing the placeholder at the moment `enqueue()` is *called* risks a
one-frame gap or duplicate in exactly the part of the feed CLAUDE.md calls
fragile (inverted list, pointwise diff, capacity window). The three-phase
design never re-keys the row, so this class of bug cannot occur.

## Photo pipeline (single photo, album tile, pasted image — one code path)

`processPhotoItem(data:index:clientMsgId:)`:
- **Quick pass**: `ImageProcessor.rgbaPixels(data)` (32px) → BlurHash + the
  32px thumbnail's own width/height as a stand-in aspect (a thumbnail
  generated by `CGImageSourceCreateThumbnailAtIndex` preserves the source's
  aspect ratio, and layout only ever reads `w/h` as a ratio) → `updateMediaPreview`.
- **Heavy pass**: `ImageProcessor.prepareForSending(data)` (1280px, JPEG 0.8) →
  `stash` to disk → final `MediaInfo` with `localPath` and the true `w/h`.

Album items run concurrently (`TaskGroup`), each updating its own index as
soon as its quick/heavy pass completes — tiles fill in independently, not
gated on the slowest sibling. `finalizeMedia` fires once, after every item's
heavy pass has finished (the wire protocol carries one `album: [MediaInfo]`
per message, so partial upload of an album isn't a thing the protocol
supports).

## Video pipeline

Reorder today's `sendVideo`: read the asset's video track `naturalSize` (near
free, no decode) and generate the poster frame + its BlurHash *before*
transcoding, not after. `beginMedia` uses the track's real aspect from the
first frame; `updateMediaPreview` lands the poster + BlurHash typically in the
low hundreds of milliseconds — far under the multi-second
`AVAssetExportSession` transcode, which now runs last and only gates
`finalizeMedia`.

## Failure semantics

- Any prep failure (stash, export) → `abandonMedia` + the existing
  `sendFailure` alert text. No new retry state: a message that never reached
  `outbox` has nothing a retry could re-upload, same as today.
- An album where one item fails prep: abandon the whole album (delete the
  row, alert), matching today's behavior where `sendPhotos` aborts entirely on
  the first failed `stash`. No partial-album send.

## Verification

- `swift test` in MsngrKit: new coverage for `beginMedia` → `updateMediaPreview`
  → `finalizeMedia` (row appears before `outbox`, `outbox` only appears after
  finalize, `abandonMedia` removes an unqueued row) and for the "not ready"
  guard (an outbox row is never created ahead of `localPath`).
- Live run on the simulator per every composer path (single photo, album,
  video, paste) — bubbles appear immediately, blurred, then resolve to the
  real preview; sends complete, checkmarks land.
- Timed report (tap → bubble visible, tap → preview resolved) for a 5-photo
  album and a video, written to `docs/qa/runs/`.
